# trellis

A replicable agentic harness for Claude Code: the always-loaded working method, git guards, hygiene of the instruction files, ratchets and project templates. This repository is both the plugin and its marketplace.

Base, the module of this repository, needs only git and node. The Cycle (issues, labels, review against the plan) and Autonomy (cloud routines, dispatcher, budget) modules are built on top of it. Of Cycle, this repository holds the mould of an issue's plan and its check, the check of the branch against that plan, and the close of the issue when its pull request is merged; `tracker.kind = none` leaves them off.

## Install in a project

1. Claude Code 2.1.330 or later (the marketplace pinned by sha and the `--scope local` install need it).
2. In the project's main checkout, install the plugin at the **local** scope, pinned to a full sha of this repository (`<sha>` is the commit to adopt; `git ls-remote https://github.com/rologr35/trellis.git HEAD` prints the latest):

   ```sh
   claude plugin marketplace add rologr35/trellis@<sha> --scope local
   claude plugin install trellis@trellis --scope local
   ```

   Both write to `.claude/settings.local.json`, which git ignores, so the main checkout stays clean: `init` asks for it clean, on the integration branch. The project scope (`--scope project`) would write `extraKnownMarketplaces` and `enabledPlugins` into `.claude/settings.json`, an uncommitted change in that checkout that the merge of `init` then collides with. `enabledPlugins` enables an installed plugin, it does not install it. `claude plugin marketplace add` does not write `autoUpdate: false`: a marketplace pinned by `owner/repo@<sha>` is not moved by an update, and `init` writes `autoUpdate: false` explicitly in the project's settings; by hand, it is the key `"autoUpdate": false` beside `source` in `extraKnownMarketplaces`.
3. `/trellis:init`: an interview, then it writes the configuration and the templates, and ends with `trellis sync`, `trellis hygiene --freeze` and `trellis doctor`.

`init` works in a worktree and writes the project-scope keys there: `extraKnownMarketplaces` with the plugin's full sha (`ref`) and `autoUpdate: false`, and `enabledPlugins`, in `.claude/settings.json`, and the CI workflow with the same sha. The merge of that branch is the only place they land; the local entries of step 2 are then redundant, and the local marketplace entry can override the project's sha with the old pin. After the merge, remove both local keys from `.claude/settings.local.json` (`extraKnownMarketplaces.trellis` and `enabledPlugins."trellis@trellis"`; `claude plugin uninstall trellis@trellis --scope local` removes only the second), and check with `claude plugin marketplace list` that the marketplace shows the project's sha. Updating the plugin is changing that sha in both places, in a pull request of its own. Changing the sha does not change the install on the machine: after the merge, bring it in line with `claude plugin marketplace add rologr35/trellis@<sha> --scope project` and `claude plugin update trellis@trellis --scope project`. The `add` rewrites `.claude/settings.json` (it reorders the keys and drops `autoUpdate: false`), so restore it with `git checkout -- .claude/settings.json`. `trellis doctor` warns while the installed sha differs from the pinned one. That step belongs to a machine and not to the merge, so the pull request that moves the sha has it as an item of **After merging**: merged, its issue keeps the label `pending-actions` until `trellis issue close <pr> --done`.

Moving the sha to 0.5.0 or later takes two edits, in the same pull request:

- `.github/workflows/trellis.yml`, by hand, from `templates/workflows/trellis.yml`: the type `closed`, `if: github.event.action != 'closed'` on the job `trellis`, and the job `closed`, which calls `consumer-closed.yml` at the same sha with its own permissions (`contents: read`, `issues: write`, `pull-requests: read`). Without it the check still passes, and `trellis doctor` warns that a merge made on GitHub closes no issue.
- The body of every pull request of an issue into the integration branch: `Closes #<n>`, **Before merging** and **After merging**. Without them `pr-check` fails from that sha on, in the pull requests already open too.

## Language

The plugin is written in English. What it writes into a project follows `project.locale`, `en` (the default) or `es`, the first question of `init`:

- the method block, from `method/en.md` or `method/es.md`;
- the templates, from `templates/en/` or `templates/es/`: `CLAUDE.root.md`, `CLAUDE.package.md`, `rule.md`, `SKILL.md`, `TESTING.md`, the mould of an issue (`issue.md`, read from the plugin and not copied) and the comments of `trellis.config`; the language-neutral ones (`settings.json`, `githooks/`, `gitignore.fragment`, `workflows/`) stay in `templates/`;
- the generated blocks (`method`, `orientation`, `commands`, `gates`, `rungs`), whose labels live in `lib/blocks.mjs`;
- the pull request sections `pr-check` requires, defined in `lib/locale.mjs`: **Summary**, **Verification** and **Setback**, and **Before merging** and **After merging** in the pull request of an issue, in en; **Resumen**, **Verificación** and **Retroceso**, and **Antes de mezclar** and **Después de mezclar**, in es;
- the words of the report of `plan-check`, defined in `lib/locale.mjs`: `Verdict: satisfied`, `Verdict: changes requested` and `Not established:` in en; `Veredicto: satisfecho`, `Veredicto: cambios pedidos` and `No establecido:` in es;
- the sections and labels of an issue's plan that `trellis issue` reads, defined in `lib/locale.mjs`: **Context**, **Approved plan**, **Layers and files**, **Risks** and **Verification** in en; **Contexto**, **Plan aprobado**, **Capas y ficheros**, **Riesgos** and **Verificación** in es;
- the narrative phrases the hygiene checks: the list of the project's locale, and always the en one, because code comments are English.

Each prose template is a file per locale rather than one file with per-locale strings: a template is mostly prose, and a file per locale keeps it readable as the text it produces. The tests keep the copies aligned: each principle of the method carries an id (`<!-- p:<id> -->`, stripped from the generated block) and both methods carry the same ids in the same order; both template folders hold the same files with the same blocks, the same `trellis.config` keys and the same placeholder names (`{{name}}`, `{{package}}` and the rest are the English ones in both; only the text around them and the free-text prompts are translated); the sections of each `issue.md` are the ones of its locale, in order; and a project written from each locale's templates passes the hygiene.

## What is there

| Piece | Where | What it does |
|---|---|---|
| Method | `method/<locale>.md` | How Claude works, on every turn. `trellis sync` copies it into the `<!-- trellis:method -->` block of the root `CLAUDE.md`, and the hygiene checks that it matches: a skill loads only when invoked, the method is needed always. |
| CLI | `bin/trellis` | `config`, `doctor`, `sync`, `hygiene`, `setup`, `worktree add\|prune`, `ratchet`, `pr-check`, `issue check\|create\|close`, `check`. |
| Issue plan | `templates/<locale>/issue.md`, `scripts/issue.sh` | The mould of the plan an issue holds, and its check: before publishing (`--body <file>`), at pick-up (`<n>`, with the amendments resolved and the dependencies closed), and at creation, with the label of its class (S, M or L). |
| Close of a merge | `scripts/issue.sh`, `.github/workflows/consumer-closed.yml`, `skills/merge/` | `trellis issue close <pr>` closes the issues of a pull request merged into the integration branch and, with actions in **After merging**, leaves them in one comment with the label `pending-actions`, which `--done` takes off. The workflow runs it for a merge made on GitHub; `/trellis:merge <pr>` is the whole path. |
| Configuration | the project's `trellis.config` | git-config format, read with `git config -f`; `lib/schema` holds the keys and their defaults. |
| Guards | `hooks/guard-git.sh` | Pushes to protected branches, branch switches in the main checkout, issues without a prior search, merges outside the allowed bases. `gh issue new` and `trellis issue create` are issue creations like `gh issue create`. |
| Git hooks | `templates/githooks/` | Ratchet, hygiene, commit message and branch name, in the clone. |
| Consumer CI | `.github/workflows/consumer-check.yml` | Hygiene, ratchet, `pr-check` and the secret scanner on every open pull request. `consumer-closed.yml` is the second workflow, run when one is merged. Neither runs a rung: a rung with `pr = true` is run by the project's own CI. |
| Skills | `skills/` | `init`, `scaffold`, `debugging`, `retro`, `merge`. |
| Agents | `agents/plan-reviewer.md`, `agents/plan-check.md` | Each in a clean context: the first checks a plan against the repository before the work, the second checks the branch of an issue against its approved plan while the pull request is a draft. |

## Where each thing runs

- The plugin's `bin/` joins the PATH of Claude's Bash tool, not a person's shell nor the hooks. A person or a git hook calls `trellis` by its path: `lib/find-trellis.sh` looks for it on the PATH and then in the `installPath` of `~/.claude/plugins/installed_plugins.json`, because the cache path changes with every version.
- The plugin's hooks use `${CLAUDE_PLUGIN_ROOT}` and need node. Without node, `guard-git` has no opinion and `trellis doctor` gives a FAIL. The native `claude` binary does not bring node.
- A plugin does not contribute `permissions`: the `deny` lives in the project's `settings.json`, and `trellis sync` generates it.
- A session hosted in the cloud reads the project's `settings.json` but does not add the marketplaces of `extraKnownMarketplaces`, so the plugin's hooks may not run there. That is why the push `deny` is in `settings.json` as well as in `guard-git`.

## The barriers and their limits

- **Consumer CI**: the real barrier, where the GitHub plan allows requiring checks. In a private repository on a plan without required checks it is advisory: nothing prevents merging with a red check. What is left is `guard-git` and the `deny` for Claude, the git hooks for the clone, and the person who does not merge on red. `trellis doctor` cannot know which plan the repository has.
- **Consumer CI and the plugin's visibility**: the consumer workflow clones the plugin at the pinned sha with no credentials, so the plugin repository has to be reachable anonymously: public, and with a public repository nothing else is configured. A private fork needs its own adaptation, which this repository does not build: its Actions access level set so that the project's repositories can call the reusable workflow, plus a token for the clone of the plugin (a secret of every consumer).
- **Git hooks**: a convenience, not a barrier. A clone without Claude and without `init` lacks them until someone runs `trellis setup`; the plugin's `SessionStart` hook runs it in every session, in the cloud too. The aggregate limits (the total of the rules) run only in CI: they are a budget shared between branches.
- **Push without a refspec**: the `deny` of `settings.json` covers the forms a permission rule can express (`main`, `+main`, `refs/heads/main`, `HEAD:main`, with or without `-C`), but not a bare `git push` on a protected branch: no pattern stops it without stopping every push. There the guard is `guard-git`, which judges the current branch and its upstream; where the plugin does not load, the method asks for an explicit refspec.
- **Directory of the command**: `guard-git` judges a push or a merge with the `trellis.config` of the directory the command runs in, after its `cd` or `git -C`. It expands what needs no execution: quotes, `~`, and the variables the same command assigns literally. A variable counts only when its assignment surely ran and lasts: one after `&&`, `||` or a pipe (or on the left of one), from a command, appended with `+=`, or set by `read`, `printf -v`, `for`, `export`, `declare`, `local`, `typeset`, `readonly` or `unset` is unresolved, and so is `~` with `HOME` unset or empty. A directory that needs the shell (`~user`, `cd -`, `$(...)`, an unresolved variable, a variable set in an earlier call) is read as the session's own. A `cd` that may not run (after `&&` or `||`), or does not last (on a side of a pipe, in the background, in a subshell), adds a directory the shell may stand in without taking the others away. When the directory a push or a merge runs in has no `trellis.config`, the config of every directory the command visited with `cd` and of the session's judges it, and the strictest answer wins. With no `trellis.config` anywhere there is no opinion, and a push is left to the `deny` of `settings.json`, a merge to nothing; except that a merge naming another repository (`-R`, `GH_REPO`) is denied then, because gh reaches it without any directory.
- **What the hook cannot judge**: parsing the shell completely is not a goal, so `guard-git` fails closed instead. A command that has `push` next to the name of a protected branch (as a word, after the quotes are removed, also as the default of `${B:-main}`, in any directory the command visited or that `GIT_DIR`, `--git-dir` or `env -C` names), or that holds `gh` and `merge`, is denied unless every git and gh invocation in it was judged: the directory and every refspec resolved (a glob or a brace list is not), no wrapper (`env`, `command`, `sh -c`, `bash -lc`, `eval`, `xargs`, an absolute path to git), no `GIT_DIR`, `GIT_WORK_TREE`, `--git-dir` or `GH_REPO`, no `git -c` on a push, no command held in a variable. The bodies of `$(...)`, backticks and `<(...)` are read as a group and judged before the command that holds them, and `$(git branch --show-current)` counts as `HEAD`. `git push --all`, `--mirror`, `--branches`, the refspec `:` and any refspec with `*` are denied outright. The deny names the part it could not judge, and the price is that an unusual form of push or merge is denied rather than parsed: the session writes the command plainly, one invocation per command. The shell may stand in at most 8 directories at once and the command visits at most 8; past that it is not judged, so a chain of `cd` cannot slow the hook down. Operators (`; & | && || ( ) { }`, newline) and redirections (`main>/dev/null`) are read in the same quote-aware pass as the words, so `git push -o 'x;y' origin main` is one push.
- **Accepted limits of the backstop**: an alias in the git configuration files (`git p origin main`), `git -c push.default=matching push` (a push with no protected name in the command), `gh api graphql` with `mergePullRequest`, `source` of a script that pushes, and a script written and then run (`cat > p.sh`, `bash p.sh`) have no protected name next to `push` in the command, so the hook does not see them; the `deny` of `settings.json` and the branch protection of the host are the barriers there.
- **Merge**: only `guard-git` judges the base of a pull request. A `deny` of `gh pr merge` would block every merge or none, because a permission rule does not see the base and a `deny` beats every `allow`. Where the plugin does not load, the merge has no guard; Base launches no cloud sessions.
- **Which GitHub account is asked**: the account `gh` has active is not always the one that sees the repository. `guard-git` (the base of a merge, the state of the issue of a branch switch), `trellis worktree prune` (the merged pull request of a branch) and `trellis issue` (the issue, its dependencies, the issue and label it creates, and the pull request and issues it closes) ask GitHub as the account of the repository's owner when `gh auth token -h github.com -u <owner>` answers a token, and give it to that one `gh` call only: the token is never printed, written or exported, and every call is a read (`view` or `list`) except the writes of `trellis issue create` (`issue create` and `label create`) and of `trellis issue close` (`issue edit` for the label, `issue comment`, `issue close` and `label create`). The owner is the one of `-R`/`--repo`, of the URL that names the pull request, or of the `origin` remote (https, `git@` or `ssh://`). With no owner (another host, no origin, an origin that does not parse, or an ssh host alias such as `git@github-work:owner/repo`, which is common with two accounts), an owner that is not signed in, or `GH_TOKEN`, `GITHUB_TOKEN`, `GH_HOST` or `GH_REPO` already set, `gh` runs as it would without the hook. When the owner is an organisation there is no account of that name, so the active account is asked. A failure is named: the merge `deny` says which account was asked and what `gh` answered, the hook says in a message that the state of an issue could not be read, and `prune` keeps the worktree and says GitHub could not be asked. The `gh` commands the session itself writes are not touched and run as the active account: a `GH_TOKEN=$(gh auth token -u <owner>)` prefix on them is still the way to choose one, and Claude Code asks permission for that form unless a person allows it in `.claude/settings.local.json`.
- **Issue plan**: `trellis issue check` is a check a session runs, not a barrier: `gh issue create` without the mould and work started on an issue that fails are not prevented. At `<n>`, a comment amends the plan only when its author is an owner, a member or a collaborator; the body counts whoever wrote it, so in a public repository the body of an issue opened from outside is read before it is taken as a plan. The check sees the form (sections, sources, paths of the integration branch, closed dependencies), not whether a plan was approved or whether the identifiers it names exist. It fetches the integration branch first; offline it says so and judges by the last fetch. Other text of a `Depends on` line is printed for a person, and does not fail.
- **Close of a merge**: `consumer-closed.yml` runs on the pull request of a branch of the repository; one of a fork has a read-only token and is skipped, and `trellis issue close <pr>` closes its issue by hand. It reads the body as it is when it runs. Closing keywords are read as GitHub reads them (`Closes`, `Fixes`, `Resolves` and their forms, one per reference), outside code and comments, and only for issues of the same repository. An issue is closed whatever is pending: the label and the comment are what remains. The comment is written once per pull request and issue, its first line being the mark, which counts when an owner, a member, a collaborator or the workflow wrote it. Two merged pull requests of the same issue share the label, so `--done` of one takes it off for both.
- **Plan check**: `plan-check` is a check a session runs, not a barrier: nothing prevents `gh pr ready` without it. It costs one subagent of the sonnet model per pull request.
- **Secret scanner**: an external tool chosen in `init` (gitleaks by default). With none configured, `doctor` warns; configured and missing, FAIL.

## `trellis doctor`

Read-only: it never writes or fetches. It exits 1 when there is any FAIL.

- **FAIL**: a `trellis.config` key outside the schema, a value outside the accepted ones of an enum key of `lib/schema` (`project.locale`, `tracker.kind`, `workspace.kind`, `rung.*.agent`, `rung.*.pr`), `workspace.kind = other` without `[hygiene] namedExt` (the extensions to declare for a stack beyond flutter, dart and node), a command name without `[command "<name>"] run`, or a `trellis.config` that does not parse (the doctor reports it and goes on diagnosing; the other subcommands stop on it); a tool of `[toolchain] require` missing or older than its minimum; `core.hooksPath` unset or other than `.githooks`; the plugin not installed or Claude Code below 2.1.330; node missing with hooks active; `ANTHROPIC_API_KEY` exported (the subscription stops being used and every token is billed as API usage, silently); a branch that is not the integration branch, the release branch or an issue branch; a configured `[command] secretScan` whose scanner is missing; a file of `[toolchain] envFile` missing (presence only, it is never read).
- **Warning**: a rung with `pr = true` that no file under `.github/workflows/` runs (it must contain the command's `run` text, or its `ci` text when set, as a plain substring search: a folded `run: >-`, a YAML comment or a commented-out step is misjudged and `npm test` is found inside `pnpm test`, so it is a hint and not a YAML parser: `pr = true` means the project's own CI runs the rung on every pull request, because the consumer workflow never runs rungs and does not install a stack's toolchain), a `.github/workflows/trellis.yml` that does not name `consumer-closed.yml` with `tracker.kind = github`, no secret scanner configured, uncommitted changes, unpushed commits, worktrees of branches that are not on origin.
- **Info**: what the release is waiting for.

## What the framework does not do, and why

- **Executor subagents that reread the repository.** A subagent starts without the session's context and rebuilds it by reading, which costs quota every time. Two checks use one each, `plan-reviewer` in Base and `plan-check` in Cycle, because a clean context is exactly what they need.
- **Status comments on issues.** The state of a piece of work lives in its branch, its commits and its pull request; a status comment is a second copy that goes stale. The one exception is the actions a merge leaves pending: once the branch is gone nothing else holds them, so `trellis issue close` writes them once on the issue, and the label says whether they are still pending.
- **Reconciliation at session start.** Rereading all the state at startup pays in every session for what few of them need. State is reread from its source when it is used.
- **Closing rituals.** A fixed step at the end gets skipped when it adds nothing. `retro` proposes a lesson only when there is one, and a person applies it.

## Development

```sh
for t in lib/*.test.sh scripts/*.test.sh hooks/*.test.sh; do /bin/bash "$t" || break; done
node --test hygiene/*.test.mjs
```

The scripts run with bash 3.2 (the macOS one): no `mapfile`, no associative arrays, and empty arrays under `set -u` are expanded with care. CI runs on ubuntu and macos, and on macos with `/bin/bash`.
